## 1. 目的と設計原則
- **表は減る、裏は積み上がる**：表では今日の残量が記録ごとに減る。裏（切り替え）では摂取量・使った額・節約額が積み上がる。
  - v1 以降：ホームは「減る」だけ（切り替えはなし）。積み上がりは下のタブの「期間」で見る（§5.5）。
- **開きに行かなくていい**：残量はロック画面のウィジェットに常に出す。アプリは記録のときだけ開く。
- **記録は数タップで終わる**：プリセットならワンタップ。写真や成分表示はGeminiが下書きし、自分は確認と修正だけ。

## 3. ドメインルール

### 3.1 1日の区切り
- **朝4:00（JST）で日付が切り替わる**。
- `day_key = (記録時刻をJSTにした値 − 4時間) の日付`。すべての集計はこの値で行う。
- 実装はユーティリティ関数1つにまとめ、境界のテストを書く（例：3:59は前日、4:00は当日）。

### 3.2 ターゲット
| ターゲット | 1日の目標 | 種類 | 単位 |
|---|---|---|---|
| カロリー | 2200 | 上限 | kcal |
| タンパク質（P） | 160 | 到達 | g |
| 脂質（F） | 50 | 上限 | g |
| 炭水化物（C） | 278 | 上限 | g |
| 使えるお金 | 1000 | 上限 | 円 |

- **到達型**：残りが0以下になったら「達成」。ウィジェットからは消える（または達成表示に変わる）。
- **上限型**：0は使い切っただけで、達成ではない。マイナスは「超過」としてオレンジで表示し、1日中表示を続ける。
- ターゲットは設定画面で追加・編集・並べ替え・無効化できる（名前・単位・目標値・種類）。v0の画面ではこの5つを想定してよい。
- 目標値を変えても過去の日には影響させない（日ごとに目標値をスナップショットして持つ。§4参照）。
- v1 以降：**目標の期間**を 1日・1週間（月曜はじまり）・1か月（1日はじまり）から選べる。週・月の目標の残量は、期間の始まりからその日までの合計で減る。
- v1.1 以降：期間が1日のターゲットは**休日の目標**を持てる（空欄なら平日と同じ）。休日は土日と国民の祝日（振替休日・国民の休日を含む）を自動で判定し、日ごとに手で休日／平日を切り替えられる（直近31日まで）。

### 3.3 お金と節約
- 固定額制。1日1000円。繰り越しはしない。
  - v1 以降：週・月の目標にもできる。v1.1 以降：休日の目標も持てる。どの場合も「その日の目標」は §3.2 のルールで決まる日ごとの値。
- 今月の節約 = 今月の各日の `(その日の目標 − その日に使った額)` の合計。超過した日はマイナスとして引かれる。
  - その日の目標：休日なら休日の目標。週・月の目標なら1日あたりに割った額（週は÷7、月はその月の日数で割る）。
- 当日分は「見込み」として含めて表示する。
- **集計に入れるのは「確定済みの日」だけ**。確定済みの日とは、記録が1件以上ある日か、「この日は記録なしで確定」を押した日（§3.5）。未記録の日は節約に入れず、記録を促す対象にする。

### 3.5 過去日の記録と記録漏れ
- 過去の日にさかのぼって記録・編集・削除できる。今日を含めて直近31日まで（未来の日には記録できない）。
- **記録漏れの日** = 直近7日のうち（今日を除く）、確定済みでない日。
- 記録漏れの日があるあいだは、今日の残り画面の一番上にバナーを出す。
  - 例：「11/21（土）の記録がありません」。複数の日があれば「記録していない日が2日あります」とする。
  - タップすると、その日の記録画面（§5.3）を開く。
  - バナーは閉じられない。記録するか確定すれば消える。
- 「この日は記録なしで確定」：その日は何も食べていない・使っていないとして確定する。押す前に確認を出す。
- 8日以上前の未記録日は、バナーには出さず、節約の集計からも外したままにする。

### 3.4 表示の文言
| 状態 | 表（残り） | 裏（積み上げ） |
|---|---|---|
| 上限型・残りあり | 残り X | 摂取 X ／ 使った ¥X |
| 上限型・超過 | 超過 X（オレンジ） | 同上 |
| 到達型・未達 | あと X | 摂取 X / 目標 |
| 到達型・達成 | 達成 ✓ | 同上 |

- 色はアクセントが青 `#1D4ED8`、超過がオレンジ `#C2410C`。色だけに頼らず、必ず文字でも状態を出す。
- v1 以降：ホームの各ターゲットに「目標 X · 摂取（使った）X」と、ゲージの右端に残りの割合（「残61%」、超過は「+13%」）を出す。ゲージは上限型・到達型とも満タンから減っていく。

## 4. データモデル（Supabase）
すべてのテーブルに `user_id uuid`（auth.users）を持たせ、RLSで本人しか読み書きできないようにする。

```sql
targets (
  id uuid pk, user_id uuid, name text, unit text,
  kind text check (kind in ('reach','cap')),
  daily_goal numeric, sort int, active bool default true,
  created_at timestamptz
)

entries (               -- 1回の記録
  id uuid pk, user_id uuid,
  recorded_at timestamptz, day_key date,
  label text,           -- 例: "プロテイン", "鶏むね肉の定食"
  source text check (source in ('preset','photo','label','manual')),
  preset_id uuid null,
  deleted_at timestamptz null  -- 取り消しは論理削除
)

entry_values (          -- 記録ごとの各ターゲットへの量
  entry_id uuid, target_id uuid, amount numeric,
  primary key (entry_id, target_id)
)

presets (
  id uuid pk, user_id uuid, label text, sort int,
  values jsonb          -- { target_id: amount }
)

day_goals (             -- 日ごとの目標値スナップショット
  user_id uuid, day_key date, target_id uuid, daily_goal numeric, kind text,
  primary key (user_id, day_key, target_id)
)

day_status (            -- 日ごとの確定状態
  user_id uuid, day_key date,
  confirmed_empty bool default false,  -- 「この日は記録なしで確定」
  primary key (user_id, day_key)
)
```

- 確定済みの日 = `entries` に有効な記録（`deleted_at is null`）が1件以上ある日、または `day_status.confirmed_empty = true` の日。
- 過去の日に記録するときは、`recorded_at` を実際に入力した時刻のままにし、`day_key` に記録先の日を入れる（`day_key` の自動計算は、日付を指定しないときにだけ使う）。

- `day_goals` は、その日最初に記録するとき（またはその日最初に集計するとき）に `targets` からコピーして作る。過去の日に初めて記録するときは、その時点の `targets` の値を使う。
- 集計用にビューかRPCを1つ用意する：`daily_summary(day_key)` → ターゲットごとに `goal / used / remaining / kind / state(ok|over|done)` を返す。

**実装での違い・追加（v1.1 時点。正確な定義は `supabase/sql/` が正本、一覧は `supabase/sql/README.md`）**

| 場所 | 違い・追加 | いつ |
|---|---|---|
| スキーマ | すべて `zanryo`（アプリから使う）／ `zanryo_private`（内部用）の中。`public` には何も作らない | 01 |
| `targets` | `key`（kcal / p / f / c / money / null）、`period`（day / week / month）、`holiday_goal`（休日の目標、null＝平日と同じ） | 01 / 05 / 06 |
| `presets` | `values` → `amounts`（予約語のため） | 01 |
| `entries.source` | `receipt` を追加 | 04 |
| `entry_values` | `user_id` を持つ（RLS を単純にするため） | 01 |
| `day_goals` | `period`、`base_goal`（その日の時点の平日の目標）、`holiday_goal`（その日の時点の休日の目標）。`daily_goal` はその日に使う目標 | 05 / 06 |
| `day_status` | `day_off`（true＝休日、false＝平日、null＝自動で土日祝） | 06 |
| RPC | `daily_summary`（期間の値と `day_used` も返す）、`range_summary`（週・月の画面用。まだ来ていない日も目標を返す）、`day_info` / `set_day_off`（休日）、`add_entry` など | 01〜06 |

## 5. 画面（PWA）

> v1 以降は画面の構成を変えた（下の固定タブ、スクロールしない画面）。今の構成は §5.5。§5.1〜5.4 の中身（何を出すか）は §5.5 の各画面に引き継いでいる。

### 5.1 今日の残り（モック `Main`）
- 記録漏れのバナー（§3.5）：記録漏れの日があるときだけ、ヘッダーの上に表示する。
- ヘッダー：日付と、「残り／積み上げ」の切り替え。日付をタップすると、日付を選んで §5.3 を開ける。
- カロリー：円形ゲージ。表では残り、裏では摂取量を表示。
- PFC：3本の横棒。到達型か上限型かを示すタグを付ける。
- 使えるお金：横棒。裏では「今月の節約（見込み）」も表示。
- プリセット：よく使う上位3件をボタンで並べる（全件はシート表示で選ぶ）。押すとすぐ記録し、トーストで「取り消す」を数秒間出す。
- 「撮影して記録」ボタンで 5.2 へ。
- 今日の記録一覧（v0では簡素な一覧でよい）：各記録を編集・削除できる。

### 5.2 撮影 → 確認 → 記録（モック `Capture`）
- 切り替え：「料理の写真」「成分表示」。
- 撮影：`<input type="file" accept="image/*" capture="environment">`。アップロード前にクライアント側で縮小する（長辺1280px程度、JPEG）。
  - 実装：撮影後に**送る範囲を枠で切り抜く**（四すみで大きさを変える）。枠は写真と同じ縦横比の台の上に置き、画面の枠と送る範囲を一致させる。送る画像は切り抜いた部分を長辺 2048px・約250万画素まで縮小した JPEG（細長いレシートの文字を読めるように）。base64 が 230万字を超えそうなら画質を下げて作り直す（サーバーの上限は 250万字）。
  - 切り替えに「レシート」を追加（§10）。撮影画面の注意書きは出さない（利用者の希望。注意点は `docs/setup-step4.md`）。
- **料理の写真**：Geminiが料理名・kcal・P・F・Cを推定する。全項目を手で直せる。分量は×0.5単位で増減。
- **成分表示**：Geminiが表示の基準（`100g` か `1袋/1個/1食` か）と各値を読み取る。基準は手で切り替えられ、基準に合わせて食べた量（g または 個数）を入力する。記録する値 = 基準あたりの値 × 食べた量。
- 「プリセットに保存」のチェック（既定はオン）。
- 「記録する」で保存して 5.1 に戻る。
- **Geminiの値はそのまま保存しない**。必ずこの確認画面を通す。

### 5.3 過去の日（モックなし。5.1と同じ見た目で作る）
- 5.1と同じ構成で、指定した日の残量と記録一覧を出す。ヘッダーに「11/21（土）の記録」と出し、今日でないことがはっきり分かるようにする。
- この画面から記録したもの（プリセット・撮影・手入力）は、すべてその日に入る。撮影画面にも、記録先の日を表示する。
- 記録が0件で未確定の日には、「この日は記録なしで確定」ボタンを出す。
- 前の日・次の日へ移動できる（今日より先には進めない）。

### 5.4 設定
- ターゲットの編集（§3.2）、プリセットの編集・並べ替え・削除。
- ウィジェット用トークンの発行・再発行（§7）。

### 5.5 v1 以降の画面構成（今の正しい形）
- **共通**：下に固定のタブ「ホーム／記録一覧／＋（記録）／期間／設定」。ホーム・記録一覧・期間はページ全体がスクロールしない。よく押すもの（日付の移動、記録なしで確定、項目・週月・グラフの切り替え）は、どの画面も下（タブのすぐ上）に置き、上は見出しと情報だけ。iPhone 16 の画面に合わせる。
- **ホーム**：見ることに徹する（記録は＋から）。カロリーの円と、ほかのターゲットの棒。記録漏れのバナー（§3.5）。今月の節約は出さない（ほかのターゲットとそろえるため。DB の集計とウィジェットには残す）。今日の目安（▼）をすべてのターゲットに出す（下の項目）。休日の目標があるときは、日付の右に「平日 ⇄／休日 ⇄」（タップで切り替え）。左右のスワイプで日付が変わる（今日より先には進まない）。
- **記録一覧**：その日の記録。タップで直す・削除。左右のスワイプで日付が変わる。
- **＋（記録）**：名前で調べる・料理を撮る・成分表示・レシート・手入力・すべてのプリセット（よく使う順）。過去の日を見ているときは、その日に入る。
- **期間**：週（月曜はじまり）と月。ターゲットごとに合計と目標、目標内／超過／未記録の日数。グラフは週が「棒／折れ線」、月が「カレンダー／棒／折れ線」。左右のスワイプで前後の週・月。日付をタップするとその日のホーム。
  - 合計と比べる目標は、記録の有無にかかわらず**期間の日数分の日ごとの目標の合計**（必ず記録する前提。まだ来ていない日も、その日の目標で数える）。ターゲットの目標の期間と画面の期間が同じなら、その期間の目標。
  - 折れ線：期間の始まり（0）からの積み上げ。点は日ごとに1つ（その日の終わりの位置、時刻では動かさない。今日の点は白抜き）。目安の線は日ごとの目標の積み上げを、期間の終わりでちょうど目標になるようにそろえたもの。下は凡例（積み上げ・目安の線）と、目安線との差の一言だけ。最後の点（今日の点は今日の分まで）と同じ位置の目安線を比べ、上限型は「目安線より X 余裕／使いすぎ」、到達型は「目安線より X 先行／遅れ」（ホームのペースとそろえる）。期間の目標を超えたら「目標を X 超えています」、到達型で届いたら「目標を達成 ✓」。過ぎた期間は「目標より X」。
- **設定**：§5.4 に加えて、目標の期間・休日の目標、写真の読み取り回数、パスワード、ログアウト、アプリのバージョン。

## 6. Edge Function: `estimate-nutrition`
> 実際の名前は `zanryo-estimate-nutrition`。mode に `receipt`（レシート）と、画像の代わりに名前を送る「名前で調べる」（Google 検索つき）を追加（§10、`docs/setup-step4.md`）。

- 入力：`{ mode: 'photo' | 'label', image: base64 }`（認証必須）。
- Geminiへは画像と指示を送り、**JSONで返させる**（response schemaを指定）。
  - photo：`{ name, kcal, p, f, c, confidence: 'low'|'mid'|'high' }`
  - label：`{ basis: 'per100g'|'per_unit', unit_label, unit_grams?, kcal, p, f, c }`
- 返ってきた値を検証してから返す（数値か、範囲は妥当か。例：0 ≤ kcal ≤ 3000）。失敗したら空の下書きを返し、画面では手入力に切り替える。
- モデルは、実装時点で画像入力に対応し、かつ**無料枠で使えるGemini（Flash系）**にする。モデル名は環境変数にする。
- **無料枠だけで使う（絶対に課金しない）**：
  - APIキーは、**Cloud Billingを有効にしていない**Google Cloudプロジェクト（AI Studioで発行したもの）で作る。課金が有効になっていなければ、上限を超えてもエラーになるだけで請求は発生しない。
  - 無料枠のレート上限に達した（HTTP 429）ときは、リトライを繰り返さず、「今は推定できません」と表示して手入力に切り替える。
  - 1日の呼び出し回数をEdge Function側で数え、上限（環境変数、初期値は無料枠より十分少ない値）を超えたらGeminiを呼ばない。
  - 実装時に、そのモデルの無料枠の上限を公式ドキュメントで確認し、READMEに書いておく。
- 無料枠では、送った画像と回答がGoogleの製品改善に使われ、人が目を通すことがある。そのため：
  - 送るのは料理・成分表示の写真だけにする。送る前に、画面で中心部分を切り抜けるようにする（人の顔や部屋の中が写り込まないように）。
  - 位置情報などのEXIFは、クライアント側で縮小するときに取り除く。
- 画像は保存しない（推定が終わったら捨てる）。

## 7. Edge Function: `widget-summary` と Scriptable
> 実際の名前は `zanryo-widget-summary`（Verify JWT はオフ。トークンのハッシュを DB で確かめる）。ウィジェットの見た目の作り直しは保留中（利用者の判断）。

- `GET /widget-summary`、ヘッダー `Authorization: Bearer <widget_token>`。
  - `widget_token` は設定画面で発行するランダムな長い文字列。DBにはハッシュだけを保存し、読み取り専用にする。
- レスポンス：
  ```json
  { "day_key": "2026-11-23", "updated_at": "...",
    "items": [ { "name":"カロリー","unit":"kcal","kind":"cap","goal":2200,"remaining":1340,"state":"ok" }, ... ],
    "month_saving": 7270 }
  ```
- Scriptable用スクリプト `widget/zanryo.js` をリポジトリに入れる。
  - トークンはScriptableの `Keychain` に保存する（スクリプトに直接書かない）。
  - `config.widgetFamily` に応じて描き分ける：
    - `accessoryCircular`：1項目をリングで表示（どの項目かはウィジェットのパラメータで選ぶ）。
    - `accessoryRectangular`：「今日の残り 1,340kcal · ¥420」と、2行目にPFC。
    - `small` / `medium`：ホーム画面用。中身は同じ。
  - 到達型で達成した項目は表示から外す。上限型は常に表示し、超過は「超過」と書く。
  - 再読み込み間隔は `refreshAfterDate` で15分後を指定する（実際の更新はiOS次第なので、PWAで記録した直後には反映されないことがある。§9参照）。
  - 通信に失敗したら、最後に取得した値と時刻を表示する。
- ※ Scriptableのロック画面ウィジェット（accessory系）の挙動は、実装の最初に実機で動作を確認すること。

## 8. 非機能
- 認証：Supabase Auth（メールのマジックリンク）。利用者は1人だが、RLSは必ず有効にする。
  - 実装：ホーム画面のアプリはメールアドレス＋パスワード（§10）。
- 更新：アプリを開いたとき・前面に戻ったとき・1時間ごとに新しい版を確かめ、自動で入れ替える（Service Worker）。設定に版（コミット）と作った日時を出す。
- オフライン：記録だけはオフラインでもキューに入れ、復帰したら送る（v0では最低限の実装でよい）。
- タイムゾーン：保存はUTC、`day_key` の計算はJST固定。
- 秘密情報（Gemini・Supabaseのサービスキー）はEdge Functionの環境変数にだけ置く。

## 9. v0の範囲と受け入れ基準
**v0に入れるもの**：§5.1〜5.4、§6、§7、§3の全ルール。

**v0に入れないもの**：通知、グラフや履歴の分析画面、複数ユーザー、Obsidian連携、データのエクスポート（v1で検討）。

**受け入れ基準**（すべて実機のiPhoneで確認する）
1. プリセットを押すと、2タップ以内で記録が終わり、残りが即座に減る。取り消しで元に戻る。
2. 3:59の記録は前日、4:00の記録は当日に入る（テストあり）。
3. 上限型が超過すると、オレンジと「超過」の文字で表示される。Pが160gに届くと「達成」になり、ウィジェットから消える。
4. 料理の写真から、確認画面に推定値が入った状態で出る。修正して記録できる。Geminiが失敗しても手入力で記録できる。
5. 成分表示を「100gあたり」と「1袋あたり」で切り替えると、記録する値が正しく計算し直される。
6. ロック画面の円形ウィジェットと横長ウィジェットに残量が表示され、記録から30分以内に反映される。
7. 裏の表示に、今月の節約（見込み）が §3.3 の式どおりに出る。未記録の日は集計に入らない。
8. 直近7日に未記録の日があると、今日の残り画面にバナーが出る。その日に記録するか「記録なしで確定」を押すとバナーが消え、その日が節約の集計に入る。
9. 過去の日に記録すると、その日の残量と今月の節約が正しく変わり、今日の残量には影響しない。

  - SQL は `supabase/sql/` を SQL Editor で番号順に流す（`supabase db push` は使わない）。消すときは `99_uninstall.sql`。
- [ ] `targets` に `key`（`kcal` / `p` / `f` / `c` / `money`、利用者が追加したものは null）を追加した。Geminiの推定値をどのターゲットに入れるか、節約の計算にどのターゲットを使うかを決めるため。
- [ ] `presets.values` は `presets.amounts` という名前にした（`values` はSQLの予約語のため）。
- [ ] `entry_values` にも `user_id` を持たせた（RLSを単純にするため）。
- [ ] 今月の節約の「当日（見込み）」は、記録が0件でも含める（目標額がそのまま足される）。
- [ ] 記録漏れの日は、使い始めた日（最初のターゲットを作った日）より前は対象にしない。
- [ ] ターゲットの目標値・種類・有効/無効を変えたら、**今日**の目標にはすぐ反映する（過去の日は変えない）。
- [ ] ウィジェットのレスポンスの `updated_at` は「今日の記録が最後に変わった時刻」。取得時刻は `generated_at` として別に返す。
- [ ] 記録は `add_entry` RPC で記録と値をまとめて保存する。クライアントが `p_id` を付けて送ると、オフラインのキューから再送しても二重にならない。
- [ ] 円形ウィジェットの項目は、ウィジェットのパラメータ（`kcal` / `p` / `money` など）で選ぶ。省略時は `kcal`。
- [ ] PWA は **GitHub Pages**（`https://yotteru.github.io/selflog/`）に置く。そのためリポジトリを公開にする（shiori と同じ）。リポジトリに秘密の値は入れない。
- [ ] ホーム画面のアプリは**メールアドレス＋パスワード**でログインする。マジックリンクは最初の1回だけ Safari で使い、そこでパスワードを決める。ホーム画面に追加した PWA は、メールのリンクを受け取れないため（iOS の仕様）。メールに確認コードを載せる方法は、Supabase の無料プランではメールの文面を変えられないので使えない。
- [ ] ステップ3では「撮影して記録」の代わりに「手入力で記録」を置いた（ステップ4で撮影を足す）。手入力から「プリセットに保存」でプリセットを作れる。
- [ ] **レシートの読み取り**を追加した（利用者の要望）。撮影画面の切り替えに「レシート」を足し、店名・合計・品目を読み取って、合計を「使えるお金」として記録する（`entries.source` に `receipt` を追加）。プリセットには保存しない。カード番号などの個人情報は読み取らないよう Gemini に指示し、送る前に切り抜く。
- [ ] 撮影画面では、写真を撮ったあとに**送る範囲を枠で決める**（§6）。枠の外は送らない。
- [ ] 料理の写真・成分表示でも「使ったお金（任意）」を入れられるようにした（外食の代金など）。
- [ ] Gemini のモデルの初期値は `gemini-flash-lite-latest`（無料枠 15 RPM / 500 RPD。2026-11-23 に AI Studio で確認）、1日の上限の初期値は 100回。
- [ ] 「今月の節約（見込み）」は、過去の日の画面でも**今日までの今月**の値を出す（過去の日に記録すると、その場で節約が変わるのを確かめられるように）。
- [ ] 記録漏れのお知らせをタップすると、記録していない日のうち**一番古い日**を開く。その日の画面の下に、ほかの記録していない日へのリンクを出す。
- [ ] 「この日は記録なしで確定」は取り消せるようにした（記録が0件のあいだだけ）。
- [ ] 今日の画面から記録したものは日付を指定せず（記録時刻から決まる）、過去の日の画面から記録したものはその日を指定して送る。
- [ ] ターゲットは削除できない（「使う」を外して無効にする）。カロリー・P・F・C・お金は単位を変えられない。
- [ ] プリセット：今日の画面のボタンは「よく使う順の上位3つ」、「すべてのプリセット」は設定で決めた並び順。
  - v1 以降：ホームにはプリセットを出さない。＋のシートに、すべてのプリセットをよく使う順に並べる。
- [ ] ログアウトすると、端末に残した記録のコピーと未送信の記録を消す（未送信があれば先に確認を出す）。
- [ ] ウィジェット用トークンは、発行したその場で1回だけ表示し、端末にも保存しない。
- [ ] **名前で調べる**を追加した（利用者の要望）。「手入力で記録」の名前の横の「調べる」で、Gemini が Google 検索で栄養成分と値段を調べて入れる（確認してから記録）。送るのは名前の言葉だけ。検索が使えないときは検索なしで1回だけ呼び直す。記録の種類（source）は manual のまま。
- [ ] **スクリーンタイム**は、自分で追加するターゲット（上限型・分）として1日1回手で入れる。iOS のスクリーンタイムの数字は Web アプリから読めないため。ウィジェットの円形は Parameter に名前（例：スクリーンタイム）を書けば出る。
- [ ] **v1（利用者の要望）**：仕様 §9 で v0 から外していた「グラフや履歴の分析画面」を入れた。週・月の表示（合計と目標・日ごとの棒・カレンダー・目標内／超過／未記録の日数）、スクロールしない画面と下の固定タブ（ホーム／記録一覧／＋記録／期間／設定）。見た目は Design モックの v1 案の段。
  - ゲージは上限型・到達型とも「満タンから減っていく」向き。% は残りの割合（超過は「+〇%」）。
  - ホームは見ることに徹する（プリセット・「残り／積み上げ」の切り替えはなし。プリセットは＋のシート、積み上げは期間のタブ）。各ターゲットに目標と使った量を出す。今月の節約は、のちに出さないことにした（下の v1.1 の後の項目）。
  - ホーム・記録一覧・期間は左右のスワイプで日付（期間）を移動する。
  - よく押すもの（日付の移動、記録なしで確定、期間の項目・週月・グラフの切り替え）は、どの画面も下（タブのすぐ上）に置く。上は見出しと情報だけ。
  - ペースの目安（▼）：（のちに「今日の目安」に変えた。下の項目）時刻（期間）の過ぎた割合から、まっすぐ減るとしたときの目安を出す。まとめて入力するもの（お金・スクリーンタイムなど）には向かないので、ターゲットごとに出す・出さないを選べる（既定はカロリー・PFC だけ。設定はこの端末にだけ保存）。「いつもとの比較」は、まとめて入力すると時刻で比べられないので入れない。
  - ターゲットごとに目標の期間（1日・1週間・1か月）を選べる。週は月曜はじまり、月は1日はじまり（どちらも朝4:00の区切り）。週・月の目標の残量は、期間の始まりからその日までの合計で減る。
  - 週・月の合計と比べる目標は、記録の有無にかかわらず期間の日数分の1日あたりの目標の合計（必ず記録する前提。利用者の要望で「記録した日だけ」から変更）。ターゲットの目標の期間と画面の期間が同じときは、その期間の目標。期間の画面は棒・折れ線（積み上げと目標・ペースの線）・カレンダー（月）を切り替えられる。
  - 今月の節約（§3.3）は、週・月の目標を1日あたりに割った額で数える。
- [ ] 写真の切り抜きは、写真と同じ縦横比の台の上に枠を置く（縦に長い写真で、画面の枠と送る範囲がずれていたため）。送る画像は長辺 2048px・約250万画素まで（細長いレシートの文字がつぶれていたため。以前は長辺 1280px）。
- [ ] 期間の折れ線は、点を日ごとに1つ（その日の終わり）に置き、時刻では動かさない（利用者の希望）。横軸の文字は点の真下。比べた結果の文は、のちになくした（下の項目）。
- [ ] **平日と休日で目標を分ける（v1.1、利用者の要望。特にお金）**：
  - 休日の目標は期間が1日のターゲットだけ（週・月の目標は期間の合計なので、日で分ける意味がない）。全部のターゲットで入れられ、空欄なら平日と同じ。
  - 休日は土日と国民の祝日を自動で判定（2020年以降の祝日法。春分・秋分は近似式で 2099年まで）。有給や休日出勤は日ごとに手で切り替える（`day_status.day_off`）。自動の判定と同じに戻すと、手動の記録を消して自動に戻る。
  - その日のスナップショットに平日・休日の両方の目標を残す（あとで休日／平日を切り替えても、その日の時点の目標で作り直せるように）。
  - 週・月の画面は、まだ来ていない日もその日の目標（休日なら休日の目標）で数える。棒は日ごとの目標の線、折れ線の目安は日ごとの目標の積み上げ。
- [x] 下から出るシート（入力画面）は `body` に直接置き（`createPortal`）、高さはキーボードを除いた見えている範囲（`visualViewport`）に合わせる。キーボードを閉じたらページを上端に戻す。保存ボタンは貼りつけない（キーボードを出している間も見えて煩わしいため。スクロールで届く）。理由: iPhone で、スクロールする枠の中のシートが切り取られ、キーボードの下に保存ボタンが隠れて押せなかったため。設定画面の中身は縮めない（縮むと見出しが上に切れる）。
- [x] ホームに今月の節約を出さない。理由: お金だけに出ていて、ほかのターゲットとそろわない（利用者の希望）。
- [x] 期間の折れ線の下は、目安線との差の一言だけ（昨日までとの比較・今日の目安は出さない）。理由: 昨日までとの比較は役に立たず、今日の目安は紛らわしい。目安線との差は数字で見たい（利用者の希望）。
- [x] 名前で調べるとき、Gemini に毎回「今日の日付（日本時間）」を伝え、検索の言葉に年や「最新」を入れ、ページの日付が新しい公式の情報を使うよう頼む。値がいつ時点か（`as_of`）も返し、画面に「情報の時点」として出す。検索せずに出した値は confidence を high にしない。理由: 古い情報（リニューアル前の値・旧価格）が使われることが多かった（利用者の指摘）。
- [x] ホームの▼は「今日の目安」：今週（目標の期間が1か月なら今月）の目標から昨日までの量を引いた残りを、今日から終わりまでの日に、日ごとの目標の割合で分けた今日の分。時刻では動かさず、日ごとに決まる。記録していない日はその日の目標どおりとみなす。▼は「今日の終わりに目安どおりなら残る量」の位置、一言は上限型「目安より X 余裕／使いすぎ」、到達型「目安まで あと X／目安を達成」、棒の下に「目安 X」。すべてのターゲットに出す（出す・出さないの設定はなくした）。今日を見ているときだけ。理由: 週単位で、今日どれだけとる（我慢する）必要があるかを知りたい（利用者の希望）。
- [x] パスワードの変更は、シートを開かず設定画面の中の「パスワードを変える」で行う（今のパスワードは聞かない。利用者の希望）。版と作った日時（日本時間）は設定画面の一番下に出す。理由: シートのボタンが iPhone で見つからなかったため。
- [x] 期間のカードは、合計の下に残りの量を大きく出し、割合はカッコで小さく添える（上限型「残り X（残34%）」、超えたら「超過 X（+13%）」、到達型「あと X（残35%）」、届いたら「達成 ✓」）。理由: 割合だけでは残りの量が分からない（利用者の希望）。
- [ ] Geminiの1日の呼び出し回数は、DB（`zanryo_private.gemini_usage`）で数える。Edge Functionは呼び出しごとに状態を持てないため。日の区切りは、無料枠の1日の上限がリセットされる太平洋時間の0時に合わせる（アプリの day_key とは別）。
